1 — What is WebsiteMocker?

WebsiteMocker is a private workshop where websites are built and tested before they go live. Think of it like a print shop's proofing room: designs are created and refined here — nobody else sees them. When everything looks right, one command sends it to your live domain.

Everything is controlled by typing commands in Claude. You don't need to know how websites are coded. You describe what you want, paste in a design, or point Claude at an existing site — and Claude handles the technical work.

The two spaces

  • Sandbox — your private workshop. Every site has a preview link you can visit at any time, but it won't appear in search engines. Change anything freely here.
  • Production — the live, public website at your custom domain. Nothing reaches here until you explicitly run the publish command.

Sites and slugs

Multiple websites live inside WebsiteMocker at once. Each has a short nickname called a slug — for example, parrot-capital or sfdy-alt-clean. You use the slug whenever you want to work on a specific site.

The seven stages

Every site moves through seven numbered stages. The stage tells you — and the live dashboard — exactly how ready a site is to go live.

2 — How it works

WebsiteMocker sits between your design and the live site. Designs come in from three sources; a sandbox preview is always available; and the live site only changes when you give the explicit publish command.

Three ways to bring a design in

  • Capture a live URL — point Claude at any existing website. It visits the page, takes screenshots, and extracts the design DNA (colours, fonts, layout structure) into the design library.
  • Paste a Claude Design artifact — create an HTML/CSS design in Claude's canvas, then paste the output directly into WebsiteMocker. Claude extracts all sections into working components automatically.
  • Read a Claude Design file as a reference — you don't have to ingest a design to use it. Paste any Claude Design artifact into the chat and ask Claude to extract a specific element, copy a colour palette, adapt a section, or use it as a template for something new. Claude reads the HTML/CSS and can work with individual parts without touching your existing site.

The wiring file

Every site has a file called wiring.json — a record card that tracks everything: the domain name, which email or newsletter service it uses, which social accounts are connected, and which stage it's at. Claude reads this file whenever you run a command, and updates it automatically when you publish.

The dashboard

There's a live dashboard at pbau3r-sfdy.github.io/WebsiteMocker/ showing all active sites, their stage, domain, and last deploy date. It reads directly from each site's wiring.json.

The contributor loop

Once a site is live, team members can add content by uploading a simple text file to GitHub — no tools required. Their upload triggers an automatic sync back into WebsiteMocker. You review it, then run /wm-publish to take it live. Nothing publishes automatically.

3 — What you need first

These are one-time setup steps. Once done, day-to-day work is just typing commands.

Claude Code The desktop app or terminal tool. This is where you type all commands.
GitHub account With access to the pbau3r-sfdy organisation — where all sites are stored and deployed from.
GitHub CLI (gh) A small tool that lets Claude talk to GitHub on your behalf. One-time install and login.
Node.js The technology that builds websites locally. Install once from nodejs.org.
WM_PUBLISH_PAT A security token (created once in GitHub) that gives Claude permission to push live updates. Set up by the operator.
Squarespace access Only needed the first time you connect a new domain. Once DNS is configured and the site is live, you never need Squarespace again — republishing updates the site directly. See below.
Squarespace: first time only

Squarespace is only involved when you first connect a custom domain to a new site. WebsiteMocker generates the exact DNS records to paste in. After that, the records are permanent — every subsequent /wm-publish updates the live site without touching DNS or requiring Squarespace access at all.

One-time setup required

The WM_PUBLISH_PAT token must be added to the WebsiteMocker repository's secrets on GitHub before the publish command can work. This is a Classic Personal Access Token with repo scope, stored as a secret named WM_PUBLISH_PAT.

Checking your setup

Open Claude Code in the WebsiteMocker folder and type:

/wm-list-sites

If you see a list of sites with their stages and domains, you're ready to go.

4 — Creating a new website

There are three ways to start, depending on where the design comes from.

Path A — From a Claude Design artifact

You've created a design in Claude's canvas (or received an HTML file). This is the most direct path when building something new from scratch.

  1. Create the site container. 
    /wm-new-site my-site-slug "My Site Name" "#3A8FD8" "hello@domain.com"
    Replace the slug, name, accent colour, and email with your own.
  2. Ingest the design. Paste your Claude Design HTML into the chat and type: 
    /wm-ingest my-site-slug
    Claude extracts all sections into components, rewrites links and asset paths, and injects any fonts. It first shows you a collision report — a list of any design settings that conflict with the base template. Type y to proceed.
  3. Preview it. Visit the sandbox preview URL Claude shows you. Refresh any time.
  4. Fill in real content. Use content commands (see Section 6) to add news posts, update the hero, and replace placeholder text.
  5. Connect services. 
    /wm-wire my-site-slug
    Walk through connecting newsletter, contact form, social handles, and the live domain. This advances the site to Stage 3.
  6. Complete legal pages. Add the Impressum and Privacy Policy. Stage 4.
  7. Run preflight. 
    /wm-preflight my-site-slug
    Claude checks every requirement for going live. Fix anything that shows as FAIL.
  8. Publish. 
    /wm-publish my-site-slug
    Claude builds the site with production settings, pushes it to GitHub, and outputs the DNS records to paste into Squarespace. This is the only step that requires Squarespace access.
About the collision report

When you ingest a design, Claude compares its colour variables against the base template. If both use --accent with different values, that's a collision. Claude lists every conflict and asks you to confirm before making changes — even with zero conflicts, type y to proceed.

Path B — From an existing website URL

You want to build something inspired by, or based on, a live site.

  1. Capture the reference site. 
    /wm-capture https://example.com
    Claude visits the URL, takes screenshots, and extracts colours, fonts, and layout structure into the design library. Works on Wix and other JavaScript-heavy sites.
  2. Instantiate a new site from the capture. 
    /wm-instantiate my-site-slug
    Claude uses the captured design plus a brand brief you provide to scaffold the site.
  3. Continue from Step 3 in Path A.

Path C — Using a Claude Design file as a template

You have an existing Claude Design artifact — perhaps a previous project, a design reference, or a template someone shared — and you want to extract specific parts without ingesting the whole thing.

Simply paste the HTML into the chat and describe what you want. Some examples:

  • "Extract the colour palette from this design and apply it to parrot-capital"
  • "Use the hero section from this artifact as a starting point for a new hero for mogwai-systems"
  • "What fonts and spacing does this design use? I'd like to match that feel."
  • "Adapt the card layout from this artifact into a news section for sfdy-alt-clean"

Claude reads the full HTML/CSS and can work with individual elements, extract tokens, or remix sections — without running a full ingest or touching any existing site files.

The design library

Every captured or ingested design is stored in the _captures/ folder with screenshots, colour palettes, and layout notes. Claude can reference any past capture when starting a new site — useful for maintaining a family resemblance across related sites.

5 — Updating an existing design

These are changes to the design itself — layout, sections, colours, the hero area — not content updates (those are in Section 6).

Replace the hero section

To change the headline, sub-headline, or call-to-action button:

/wm-update-hero my-site-slug

Claude asks for the new text and optional background image, writes the changes, and you can preview immediately.

Add a new design section

If you've created a new section in Claude Design and want to add it without replacing anything else:

/wm-ingest my-site-slug

When prompted for mode, choose section. Paste the HTML for just that section. Claude creates a new component file and prints the one import line you need to add to your page — nothing else is touched.

Update service connections

If you change your newsletter provider, add a contact form, or connect new social accounts:

/wm-wire my-site-slug

After any design change

The sandbox preview rebuilds automatically. When you're happy, run /wm-publish my-site-slug to push it live.

No Squarespace needed for updates

Republishing an already-live site never requires Squarespace access. DNS records are permanent once set. /wm-publish rebuilds and redeploys the site directly — your domain, SSL certificate, and search engine settings are all preserved automatically.

6 — Publishing new content

Content — news posts, job listings, announcements, blog articles — is added separately from design changes. There are two paths: you add it yourself via Claude Code, or a team member adds it on GitHub.

Adding content yourself (as operator)

Each command walks you through a short Q&A — Claude asks for the title, date, body text, and any images, then writes and commits the file.

Content typeCommandWhat it creates
News post /wm-add-news Appears at /news/. Press releases, updates, milestones.
Blog article /wm-add-blog Appears at /blog/. Longer editorial pieces.
Job listing /wm-add-job Appears at /jobs/. Includes department, location, type, open/closed status.
Announcement /wm-add-announcement Appears at /announcements/. Short, dated notices.

After Claude commits the file, run /wm-publish my-site-slug to make it live.

Brand consistency check

If your site has a brand kit (set up via /wm-wire), Claude checks each new post before committing:

  • Hashtag suggestions — Claude proposes relevant tags from your brand kit.
  • Avoid list scan — if the draft uses a word on your avoid list, Claude flags it. You can still proceed.
  • Vocabulary nudges — if the draft could use a preferred brand term, Claude notes it as a suggestion.

Team contributors adding content via GitHub

Once /wm-init-collab has been run for a site, team members can add content without any tools — just a GitHub account.

  1. The contributor goes to the production repository on GitHub (e.g. github.com/pbau3r-sfdy/starflight-dynamics)
  2. They navigate to content/news/ (or whichever section applies)
  3. They click Add file → Create new file, name it YYYY-MM-DD-title.md, write the content, and commit
  4. GitHub automatically sends the file to WebsiteMocker
  5. You review the sync commit in WebsiteMocker, then run /wm-publish to take it live
Content never goes live automatically

A contributor push triggers a sync into WebsiteMocker, but not a publish. The live site is unchanged until you run /wm-publish. This gives you a review step before anything goes public. Deleting a file from the contributor repo does not remove it from the live site — content is additive only.

Making a production repo contributor-ready

Run this once after a site goes live. It installs contribution guidelines, issue templates, and the auto-sync into the production repo:

/wm-init-collab my-site-slug

7 — Command reference

All commands are typed in Claude Code while inside the WebsiteMocker folder.

Building and publishing

CommandWhat it does
/wm-new-siteCreate a blank new site. Requires slug, name, accent colour, and contact email.
/wm-captureVisit a live URL and extract its design DNA — colours, fonts, layout — into the design library.

/wm-publishBuild with production settings and push live. Requires Stage 5. Squarespace DNS only on first publish.

Asking for help

For any task, describe what you're trying to do in plain language and Claude will suggest the right command and walk you through it.
