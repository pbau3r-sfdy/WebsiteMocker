<objective>
Author the contributor-facing bundle every production repo receives: a CONTRIBUTING.md defining the
two-tier model and the review expectation, three structured YAML issue forms with auto-labelling, a
config.yml disabling blank issues, and the `content-ci.yml` workflow that dispatches the sync.

Purpose: This is the entire contributor surface and the sending half of the loop. Plan 01 built the
receiver; without these templates a contributor has no documented path, no structured issue channel,
and no trigger.

Output: a new `_templates/` directory containing six files. Nothing is installed into a production
repo by this plan — Plan 03 builds the installer.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| contributor → production repo `main` | contributors hold write access and can modify any file on `main`, including `.github/workflows/content-ci.yml` |
| production repo secrets → GitHub Actions runtime | `WM_DISPATCH_PAT` is readable by any workflow a contributor can author on `main` |
| contributor → GitHub Issues | untrusted free text enters the operator's triage queue |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-07 | Information disclosure | `WM_DISPATCH_PAT` in `content-ci.yml` | mitigate | The stored credential is a fine-grained PAT scoped to `contents: write` on `pbau3r-sfdy/WebsiteMocker` only. A contributor who edits `content-ci.yml` to echo the secret gains the ability to trigger a content sync and write WebsiteMocker contents — not to publish to `gh-pages` on any production repo and not to reach any other org repo. `WM_PUBLISH_PAT` is excluded from production repos and asserted absent from this file |
| T-04-08 | Elevation of privilege | `on.push.paths` filter | mitigate | `paths: ['content/**/*.md']` restricts the trigger to Markdown under `content/`; editing `CONTRIBUTING.md` or any `.github/` file dispatches nothing. This also contains a workflow-file edit: the modified workflow still only runs on a content push |
| T-04-09 | Denial of service | dispatch flood from rapid pushes | mitigate | `concurrency: content-ci-${{ github.ref }}` with `cancel-in-progress: true` collapses a burst into one dispatch; the per-slug concurrency in `content-sync.yml` (Plan 01, T-04-04) serialises the sync |
| T-04-10 | Tampering | issue-template auto-labels | mitigate | Label names are fixed to `content-request`, `design-change`, `bug` and pre-created by Plan 03. GitHub silently drops unknown labels, so a mismatch degrades to unlabelled rather than mislabelled. Labels are declared per-template, never in `config.yml`, which does not support them |
| T-04-11 | Spoofing | blank issues bypassing templates | mitigate | `blank_issues_enabled: false` removes the free-form path, so every inbound request carries structured fields and a label |
| T-04-12 | Tampering | contributor pushes a non-`.md` file into `content/` | mitigate | Defence in depth: this `paths` filter matches only `*.md`, and the Plan 01 sync independently copies only `find -type f -name '*.md'`. Neither layer alone is trusted |
| T-04-29 | Repudiation | contributor believes a push published the site | mitigate | Decision D-A7 is enforced in the template text and by a grep gate: CONTRIBUTING.md must contain a review expectation and must not contain `rebuilds automatically`. A contributor who believes their push is already live may never follow up on a stalled review |
