<objective>
Build the WebsiteMocker side of the contributor loop: a `content-sync.yml` workflow that receives a
`content-updated` dispatch from a production repo, pulls the contributor's Markdown into
`sites/<slug>/src/content/`, and commits it to WebsiteMocker `main` — and stops there.

Purpose: Per the locked decision in `04-DISCUSS-CHECKPOINT.json`, WebsiteMocker is the canonical
source and there is **no auto-publish**. A contributor push must land content in WebsiteMocker for
operator review; going live remains a deliberate `/wm-publish` action. That means this is a new,
separate workflow — `publish.yml` is not touched at all, which also keeps the Phase 1 JamesIves
git-remote ordering hazard out of scope entirely.

Output: `_scripts/verify-phase-04.sh` (the phase-wide verification harness every later plan gates on)
and `.github/workflows/content-sync.yml`.
</objective>

    2. `Checkout` — `actions/checkout@v7` with `token: ${{ secrets.WM_PUBLISH_PAT }}` and

       pushes back to WebsiteMocker `main`, which `GITHUB_TOKEN` cannot do.

       review is harmless for a site at any stage, and the stage gate stays where it belongs, in
       publish.yml.

    4. `Sync content` with `env:` entries `PROD_REPO: ${{ steps.wiring.outputs.prod_repo }}` and
       `SLUG: ${{ steps.slug-step.outputs.slug }}`. Body, in order:

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| production repo → WebsiteMocker Actions | the `repository_dispatch` payload crosses from a repo with contributor write access into WebsiteMocker's privileged workflow runtime |
| production repo `main:content/` → WebsiteMocker source tree | contributor-authored files are committed into the canonical repo |
| synced content → live site | separated by a mandatory human step (D-A3), which is itself a control |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Elevation of privilege | `Resolve slug` step | mitigate | `client_payload.slug` is passed via the `DISPATCH_SLUG` env var and never interpolated into a `run:` body; validated against `^[a-z0-9-]+$` in-step before `$GITHUB_OUTPUT` is written, and re-asserted by the `node -e` guard in `Read wiring.json` |
| T-04-02 | Tampering | `Sync content` copy loop | mitigate | `find -type f -name '*.md'` excludes symlinks (type `l`) and every non-Markdown file, so a contributor cannot inject a workflow file, a script, or a symlink escape into the WebsiteMocker tree |
| T-04-03 | Spoofing | dispatch sender | accept | Any holder of a token with `contents: write` on WebsiteMocker can send the event. Blast radius is bounded by D-A3: the worst outcome is unreviewed Markdown sitting in a git commit on `main`, visible in history and never served to users until the operator publishes |
| T-04-04 | Denial of service | sync job queue | mitigate | `concurrency` group is per-slug with `cancel-in-progress: false`, so a burst of dispatches for one site serialises instead of racing `git push origin main` |
| T-04-05 | Information disclosure | `WM_PUBLISH_PAT` | mitigate | Used only for the WebsiteMocker checkout and the WebsiteMocker origin URL. The production repo clone uses a plain public HTTPS URL with no credential, so the PAT is never sent to a production repo host path |
| T-04-06 | Elevation of privilege | unreviewed content reaching production | mitigate | The sync workflow contains no build and no deploy step, asserted by grep gates on `build-single`, `JamesIves`, `CNAME`, and `robots`. Publication requires the operator to run `/wm-publish`, which retains the Phase 1 `stage >= 5` validation |
| T-04-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs in this plan. Phase 4's only new supply-chain dependency is the GitHub Action `peter-evans/repository-dispatch@v4`, introduced in Plan 02 and audited in 04-RESEARCH.md |
</threat_model>
