<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator browser → GitHub token settings | a mis-scoped token here is deployed to four contributor-writeable public repos |
| installer → four live production repos | writes a new default branch to repos that are currently serving production traffic |
| web-UI contributor commit → live site | the first real traversal of the untrusted-input path built in Plans 01–03 |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-23 | Elevation of privilege | WM_DISPATCH_PAT scope at mint time | mitigate | Task 1 acceptance criteria require visual confirmation that repository access is `pbau3r-sfdy/WebsiteMocker` only and that `Contents: Read and write` is the sole granted permission; Actions, Workflows, and Administration are explicitly listed as must-remain-No-access |
| T-04-24 | Information disclosure | token value in transcript or git history | mitigate | Task 1 instructs that the value is never pasted into chat, files, or commit messages, and asserts `git log -p -1 \| grep -ciE 'github_pat_\|ghp_'` returns 0 |
| T-04-25 | Denial of service | rollout breaking a live site | mitigate | Dry run precedes every confirmed run; execution order starts with the lowest-risk repo; the run halts on first failure rather than continuing; and post-rollout acceptance requires HTTP 200 from all four production domains plus proof that `gh-pages` still exists on every repo |
| T-04-26 | Tampering | first untrusted payload through publish.yml | mitigate | Task 3 requires reading the `Resolve slug` step log to confirm the slug resolved and validated, which is the live exercise of the T-04-01 injection guard. A run that fails at `Resolve slug` is the control working, not a defect |
| T-04-27 | Repudiation | unclear whether the rebuild was automatic | mitigate | Acceptance criteria assert the publish run's `event` field is literally `repository_dispatch` (not `workflow_dispatch`) and that zero operator commands were issued between the web-UI commit and the live result — the automation claim is verified by the trigger type, not by inference |
| T-04-28 | Tampering | leftover test content on a live site | mitigate | Task 3 step 9 removes the canary post from both the production repo and WebsiteMocker and republishes; acceptance requires the post to be absent from the live news index afterwards |
| T-04-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs. `peter-evans/repository-dispatch@v4` now executes for the first time in production; it was audited in 04-RESEARCH.md (5+ years, 50M+ workflow runs, known maintainer) and runs in the production repo with only `WM_DISPATCH_PAT` available to it |
