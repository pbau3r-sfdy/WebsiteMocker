<objective>
Author the contributor-facing bundle that every production repo receives: a CONTRIBUTING.md that
defines the two-tier model, three structured YAML issue forms with auto-labelling, a config.yml
that disables blank issues, and the `content-ci.yml` workflow that dispatches a rebuild.

Purpose: This is the sending half of the rebuild loop and the entire contributor surface. Plan 01
built the receiver; without these templates a contributor has no documented path, no structured
issue channel, and no automated trigger.

Output: a new `_templates/` directory containing six files. Nothing is installed into a production
repo by this plan — Plan 03 builds the installer.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| contributor → production repo `main` | contributors hold write access and can modify any file on `main`, including `.github/workflows/content-ci.yml` |
| production repo secrets → GitHub Actions runtime | `WM_DISPATCH_PAT` is readable by any workflow that a contributor can author on `main` |
| contributor → GitHub Issues | untrusted free text enters the operator's triage queue |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-07 | Information disclosure | `WM_DISPATCH_PAT` in `content-ci.yml` | mitigate | The stored credential is a fine-grained PAT scoped to `contents: write` on `pbau3r-sfdy/WebsiteMocker` only. A contributor who edits `content-ci.yml` to echo the secret gains the ability to trigger WebsiteMocker builds and to write WebsiteMocker contents — not to publish to `gh-pages` on any production repo and not to reach any other org repo. `WM_PUBLISH_PAT` is explicitly excluded from production repos and asserted absent from this file |
| T-04-08 | Elevation of privilege | `on.push.paths` filter | mitigate | `paths: ['content/**/*.md']` restricts the trigger to Markdown under `content/`; a contributor editing `CONTRIBUTING.md` or any `.github/` file does not cause a production rebuild. This is also the containment for a workflow-file edit: the modified workflow only runs on a content push |
| T-04-09 | Denial of service | dispatch flood from rapid pushes | mitigate | `concurrency: content-ci-${{ github.ref }}` with `cancel-in-progress: true` collapses a burst of pushes into one dispatch; the downstream per-slug concurrency in `publish.yml` (Plan 01, T-04-04) serialises the rebuild |
| T-04-10 | Tampering | issue-template auto-labels | mitigate | Label names in template frontmatter are fixed to `content-request`, `design-change`, `bug` and pre-created by Plan 03; GitHub silently drops unknown labels, so a mismatch degrades to unlabelled rather than mislabelled. Labels are declared per-template, never in `config.yml`, which does not support them |
| T-04-11 | Spoofing | blank issues bypassing templates | mitigate | `blank_issues_enabled: false` in `config.yml` removes the free-form issue path, so every inbound request carries structured fields and a label |
| T-04-12 | Tampering | contributor pushes a non-`.md` file into `content/` | mitigate | Defence in depth: the `paths` filter here only matches `*.md`, and the Plan 01 content-sync step independently copies only `find -type f -name '*.md'`. Neither layer alone is trusted |
| T-04-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs. The single new supply-chain dependency is the GitHub Action `peter-evans/repository-dispatch@v4`, audited in 04-RESEARCH.md Package Legitimacy Audit (5+ years, 50M+ workflow runs, known maintainer, approved). Floating major tag is accepted for now with an inline comment recording SHA-pinning as the hardening step |
</threat_model>
