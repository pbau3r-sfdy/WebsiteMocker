<objective>
Make WebsiteMocker's `publish.yml` able to receive an automated rebuild request from a production
repo and pull the contributor's new content in before building.

Purpose: This is the receiving half of the Phase 4 rebuild loop. Without it, `content-ci.yml` in a
production repo (Plan 02) has nothing to dispatch to, and a contributor's pushed `.md` file would
never reach the build source. This plan also creates the phase-wide verification harness that every
later plan in Phase 4 gates on.

Output: `_scripts/verify-phase-04.sh` (new) and a modified `.github/workflows/publish.yml` with a
`repository_dispatch` trigger, a slug-resolution step, and a content-sync step.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| production repo → WebsiteMocker Actions | `repository_dispatch` payload crosses from a repo with contributor write access into WebsiteMocker's privileged workflow runtime |
| production repo `main:content/` → WebsiteMocker build source | contributor-authored files are copied into the tree that produces the live site |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Elevation of privilege | `Resolve slug` step in publish.yml | mitigate | `client_payload.slug` is passed via the `DISPATCH_SLUG` env var, never interpolated into a `run:` body; validated against `^[a-z0-9-]+$` in-step before `$GITHUB_OUTPUT` is written, and again by the existing `node -e` guard in `Read and validate wiring.json` |
| T-04-02 | Tampering | content-sync step in publish.yml | mitigate | Copy loop uses `find -type f -name '*.md'` — symlinks (type `l`) and every non-Markdown file are excluded, so a contributor cannot inject a `.yml`, a script, or a symlink escape into `sites/<slug>/` |
| T-04-03 | Spoofing | `repository_dispatch` sender | accept | Any holder of a token with `contents: write` on WebsiteMocker can send the event. Blast radius is bounded: the payload only selects which already-configured, stage-≥5 site rebuilds. No new content or code can be introduced through the payload itself. |
| T-04-04 | Denial of service | publish workflow queue | mitigate | `concurrency.group` is per-slug with `cancel-in-progress: false`; a flood of dispatches for one site serialises into a single queued run rather than spawning parallel builds |
| T-04-05 | Information disclosure | `WM_PUBLISH_PAT` in the sync step | mitigate | The PAT is used only in the `git remote set-url` for WebsiteMocker's own origin. The production repo clone uses a plain public HTTPS URL with no credentials, so the PAT is never sent to the production repo host path |
| T-04-06 | Tampering | git `origin` remote | mitigate | Content sync runs before the JamesIves step; the post-JamesIves `git remote set-url origin` in `Update wiring.json stage 6` remains the last remote operation, so the wiring.json commit-back cannot be redirected to the production repo |
| T-04-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs in this plan — the only new dependency in Phase 4 is the GitHub Action `peter-evans/repository-dispatch@v4`, introduced in Plan 02 |
</threat_model>
