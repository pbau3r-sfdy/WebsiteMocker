<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI/CD env -> Astro build config | `SITE_URL` / `SITE_BASE` env vars cross into `_core/astro.config.mjs` and determine the emitted `site` and `base` for every scaffolded site |
| `_scripts/new-site.sh` -> `_core` templates | operator-supplied slug is `sed`-substituted into `{{SITE_SLUG}}` inside config files |
| verification harness -> repository files | `verify-phase-08.sh` reads repo files and emits pass/fail; it is a gate other plans trust |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-01 | Tampering | `_core/astro.config.mjs` `{{SITE_SLUG}}` token | mitigate | `verify-phase-08.sh hsk03` asserts the literal `{{SITE_SLUG}}` is still present, so a future edit cannot silently break `new-site.sh` sed substitution |
| T-08-02 | Spoofing | `SITE_URL` env var at build time | accept | Value is set only by `publish.yml` and by the operator; a wrong value produces wrong canonical URLs but no privilege gain. Fallback is the pinned `https://pbau3r-sfdy.github.io`. |
| T-08-03 | Tampering | `SITE_BASE` env var path injection | accept | Astro validates `base` as a path string at build time; output is static HTML with no server-side path resolution. No user input reaches this at runtime. |
| T-08-04 | Repudiation | `verify-phase-08.sh` self-matching grep gates | mitigate | All `#384AD3` assertions are scoped to named target files; the harness never greps itself or the repo root, and comment lines are stripped by `count_in`/`count_re` before counting |
| T-08-05 | Information disclosure | crestworks `Layout.astro` token bridge | accept | Only colour, font, and spacing literals are added. No secrets, no API endpoints, no PII. |
| T-08-SC | Tampering | npm/pip/cargo installs | mitigate | This plan installs no packages. `npx astro build` resolves the already-locked `astro ^5.0.0` from the existing workspace lockfile — no new dependency enters the tree, so no package legitimacy checkpoint is required. |
</threat_model>
